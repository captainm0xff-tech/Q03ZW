1 Protocol description

A command frame consists of the following parts.

Command identifier (TAG).

LENGTH: the length of VALUE in bytes. This is an 8-bit field with a maximum value of 255.

DATA: see the definitions below.

The extended protocol primarily supports payloads longer than 255 bytes.

EXT_LENGTH: the combined length of EXT_TAG, HEAD CRC, and VALUE.

VALUE: the command-specific payload, identified by EXT_TAG.

2 Bluetooth control and status commands (BLE)

The app uses this Bluetooth protocol to discover nearby devices and control nearby CPS devices. The payload generally begins with the device serial number.

#define AP_STA_UUID "ACA0EF7C-EEAA-48AD-9508-19A6CEF6B356"
#define DEV_IP_V2_UUID "90753043-6E40-4590-AFF6-5B48F6412E2F"

The following two main Bluetooth characteristics are used:

1) AP_STA_UUID: write TAG=0x01 or TAG=0x06 to configure AP or STA mode. For read operations, the device returns TAG=0x03 or TAG=0x04.

2) DEV_IP_V2_UUID: read operation; the device returns TAG=0x07.

2.1 App command to configure AP mode (TAG 0x01)

2.1.1 Payload description

TAG 0x01 configures a connected device to use AP mode. The payload structure is app_set_dev_wifi_apmode_t.

2.1.2 VALUE structure definition

typedef struct {
    char product_sn[24]; // char product_sn[24] = "CPS202302281025"; assignment using strcpy is also supported
    uint8_t workstatus; // 0x02: AP mode; other values currently have no defined meaning
    uint8_t frequency_mode; // 0x0: 2.4 GHz band; 0x1: 5 GHz band
    uint8_t set_unit_type; //0 default
    uint16_t devVideoHeight; // Set resolution to 1080
    uint8_t devVideoBitrate; // Set bitrate to 4 (unit: Mbs, as written in the source)
    uint8_t videofps; // Actual frame rate; the current Q03ZW configuration uses 25 or 30, not a 0/1/2 enumeration
    uint8_t CountryCode[3]; //(alpha-2 country codes defined by ISO 3166-1)
} app_set_dev_wifi_apmode_t;

product_sn is provided in Device Name in the Bluetooth scan response and is also included in the advertising packet.

Ensure product_sn and workstatus are correct. If either is incorrect, the device returns immediately without any notification; this must be detected during integration testing.

1) While switching modes, the device ignores incoming commands without any notification.

2) If the requested mode matches the current network mode, the status returned by TAG 0x07 does not change. The device performs no operation and returns immediately.

3) If the requested mode differs from the current mode, wlan_state in TAG 0x07 first changes to 0x03. On successful switching it changes to 0x02; on failure it changes to 0. The device saves the last requested mode and uses it to configure the network after the next reboot.

3 TCP control protocol

Protocol structures use 1-byte packing (#pragma pack(1)); do not transmit structures using the compiler's default alignment. See the payload length table; skip heartbeat bytes beyond the fields defined here according to LENGTH.

typedef signed char sint8_t;
typedef unsigned char uint8_t;
typedef unsigned short uint16_t;
typedef unsigned int uint32_t;
#pragma pack(1)

After discovering the device over Bluetooth and configuring and connecting to Wi-Fi, the app establishes a socket connection and sends control commands over TCP. These commands control image parameters, operating modes, focus, zoom, and other functions. The frame header, trailer, and checksum follow Section 1. The following sections define TAG and VALUE.

1) The app sends control commands and firmware package data to device port 19017. The device returns reception status for certain control commands and firmware transfers on port 19017. The app also reports streaming status on port 19017 when connecting and whenever the status changes. The app must send a keepalive heartbeat to port 19017 once per second. If the device receives no heartbeat for more than 10 seconds, it disconnects and resumes listening.

2) The device sends heartbeat data to the app through port 19015 once per second.

3) App control commands, device status responses, and device heartbeats must all carry the SN. When establishing a connection, send TAG 0x6a and TAG 0x14 to start device encoding.

3.1 App lens control command (TAG 0x10)

The current CA handles ctrlnum values 0x1 through 0x4 only. Focus mode afmode=2 selects area focus; the original Rack description has been corrected to match the implementation. The previous Tof description for afmode=3 has no corresponding handler in the reviewed CA code.

TAG is 0x10. Length can be obtained directly using sizeof on the following payload structure.

typedef struct {
    char product_sn[24]; // char product_sn[24] = "CPS202302281025"; assignment using strcpy is also supported

3.10 App time synchronization command (TAG 0x1a)

The time synchronization VALUE is fixed at 39 bytes. Tformat occupies 15 bytes: in timestamp mode, clear the structure, fill mstime, timeZone, and timeDelta, and explicitly set Tformat.date[14] to 1. If this byte is 0, CA processes a 14-digit date string. timeZone is an integer offset in hours, positive east of UTC (for example, +8); the accepted range is -12 to +12 and does not represent half-hour time zones. timeDelta is the RTT in milliseconds: 0 performs baseline synchronization; a positive value below 60 is used for RTT/2+33ms compensation only if it improves on the previous RTT. Negative values do not adjust the time.

Synchronize time using the mstime timestamp format.

App-to-device payload

typedef struct {
    char product_sn[24]; // char product_sn[24] = "CPS202302281025"; assignment using strcpy is also supported
    union {
        char date[15]; // Date format
        struct {
            unsigned long long mstime; // 64-bit UTC timestamp (time zone 0), in milliseconds
            signed char timeZone; // Integer hours, -12 to +12; positive east of UTC, for example +8 for Beijing time
            short timeDelta; // Previous round-trip time (RTT) in ms; 0: baseline synchronization; a positive value must be below 60 to qualify for compensation
        };
    }Tformat;
} app_set_time_t;

The device also replies using TAG 0x1a, with the following structure.

3.31 App command to configure RTMP streaming (TAG 0x36)

Example: a 300-byte URL excluding NUL is sent in three fragments, all with url_size=300. The pairs (url_offset, URL bytes in fragment) are (0,128), (128,128), and (256,44); LENGTH is 246 for every fragment. Zero-fill the unused rtmp_url tail. CA terminates the reassembled string.

Every fragment receives a TAG 0x36 set_rtmp_state_t response (25 bytes). set_state=0 means the fragment was accepted; for the final fragment, it also means the configuration was applied. set_state=1 indicates failure. Configuration is not applied until all fragments arrive. Wait for each response before sending the next fragment. After a connection change or fragment error, resend the entire URL from offset=0; resuming from an acknowledged intermediate fragment is unsupported. This acknowledgment does not indicate a successful RTMP server connection; query TAG 0x5c separately.

Extended URL fragmentation: send fragments sequentially over the same connection, starting at url_offset=0. Each subsequent offset must equal the number of bytes already received; copy min(128, url_size-url_offset) bytes per fragment. url_size, enable, and PowerOnPushEn must match across fragments; the username, password, and other settings come from the first fragment. url_size may exclude NUL or include one trailing NUL. Data after an embedded NUL is rejected. url_size must not exceed 512.

LENGTH distinguishes the structures: app_set_rtmp_t is 234 bytes and app_set_rtmp_ext_t is 246 bytes; the current CA rejects other lengths. BitMaskByte1.bit1 indicates extended RTMP protocol support. A valid URL must use rtmp:// or rtmps://, contain a nonempty host and path, and contain no spaces, control characters, or DEL. The current RTMP_URL_CAP is 512, allowing at most 511 URL bytes excluding the terminating NUL, rather than the 4096 bytes mentioned in the old internal buffer comment.

    char password[40]; // Password; initially defaults to NULL

3.51 App network configuration (Q03ZW New), TAG 0x66

This response has no separate set_state field; receiving the structure does not necessarily indicate a successful setting. Invalid static addresses cause set_networke_info to fail. The app should compare the returned address with the requested value and, in DHCP mode, wait for an actual lease.

5 Camera Discovery and Connection

Recommended sequence: discover the camera over Bluetooth → read its IP address and Wi-Fi information → repeat Bluetooth network setup if necessary → establish TCP control and heartbeat connections → send TAG 0x6a to configure encoding → send TAG 0x14 with pushstream=1 to start encoding → start RTSP live preview. The following procedure assumes that the phone and camera use the same Wi-Fi network.

5.1 Bluetooth Discovery and Device Identification

  1. Enable Bluetooth, obtain the scan and connection permissions required by the phone's operating system, and scan for nearby BLE devices.
  2. Parse the advertisement's Manufacturer Specific Data and initially filter devices by manufacturer ID 0x005D. The manufacturer data contains the camera's SN string, for example CPS202302281025. In the raw advertising field, the manufacturer ID is encoded as the two bytes 5D 00, followed by the SN. If the phone's Bluetooth API provides the manufacturer ID separately, read the SN directly from the corresponding data value.
  3. Use the advertised Local Name to display the device name and the SN to distinguish devices. Names can be changed and are not unique identifiers; the CPS prefix alone does not identify the target camera.
  4. After the user selects a device, establish a BLE connection and discover its GATT services. Confirm that the network setup service and characteristics listed below are present. Then read product_sn from the IP characteristic and verify that it matches the selected device's advertised SN. Use that same SN in subsequent commands.

The manufacturer ID is an initial filter, GATT services and characteristics confirm the interface, and the SN identifies the selected device.

5.2 Reading the IP Address and Bluetooth Network Setup

Perform a GATT read on DEV_IP_V2_UUID to receive a complete TAG 0x07 protocol frame with VALUE structured as dev_ipV2_t. Validate the header, length, checksum, and trailer, then parse product_sn, wlan_ip, wlan_state, wifi_ssid and wifi_bssid. For the data format, see 2.6 Device IP Address Response.

When the camera is in STA mode (wlan_state=0x01), returns a valid IP address, and reports Wi-Fi information matching the phone's current network, use that IP address to establish the TCP connections. Use the SSID to check the target network and the BSSID when the specific access point must be identified. Even with a matching SSID, verify network reachability through an actual TCP connection.

If no valid IP address is available, or the camera's Wi-Fi information does not match the phone's current Wi-Fi network, repeat Bluetooth network setup:

  1. Write to AP_STA_UUID using TAG 0x06 with VALUE structured as app_set_dev_wifi_stamodeV2_t. Fill in the target camera SN, the phone's current Wi-Fi SSID and password, and the required network parameters. Set workstatus=0x01, distribution_network_sign=0; for DHCP, set ip_state=0. Field definitions are provided in 2.3 STA Network Setup Command.
  2. Wait for the device to switch networks, then read the IP characteristic again. Continue waiting while the network is switching (wlan_state=0x03) or the IP address is not ready. If an error or connection timeout occurs, check the network setup parameters.
  3. You can read AP_STA_UUID for a TAG 0x04 response confirming STA mode. Determine whether a usable IP address is available from the subsequent TAG 0x07 response. Verify the SN, IP address, and Wi-Fi information before establishing the TCP connections.

5.3 Establishing TCP Control and Heartbeat Connections

After obtaining the camera IP address, the app should initiate and maintain two TCP connections to the same camera:

ConnectionCamera portPurpose
Control connection19017Send control commands, including TAG 0x6a and TAG 0x14, and receive the corresponding status responses.
Heartbeat connection19015Receive device TAG 0x16 heartbeats, normally once per second, to update device status.

The app initiates both connections to the camera's listening ports. Send TAG 0x14 over the control connection on 19017; receive device heartbeats on 19015. Parse complete protocol frames from the TCP byte stream, handling coalesced and fragmented frames. Verify that heartbeats and status responses carry the target device SN. Heartbeat length may vary by firmware version but is fixed for a given version.

5.4 Setting Encoding Parameters and Starting Encoding

  1. Send TAG 0x6a over the control connection on 19017, with VALUE structured as app_NetCodingParam_t, specifying the target SN, preview resolution, codec, frame rate, and bitrate. NetCodingTypeFormat is 0 for H.264 and 1 for H.265; videofps carries the actual frame rate, 25 or 30; CodingMaxRate is in Mbps, and CodingMinRate is in Kbps; 0 disables dynamic bitrate. Set reserved fields to 0. For the complete definition, see 3.54 Network Encoding Parameters (TAG 0x6a).
  2. Next, send TAG 0x14 over the same control connection, with VALUE structured as app_resp_heartbeat_t. Fill in the target product_sn and set pushstream=1 to request encoding and preview streaming. The field to set to 1 is pushstream. For the data format, see 3.5 App Heartbeat Reply (TAG 0x14).
  3. During preview, maintain both connections and reply with TAG 0x14 at the heartbeat interval, keeping pushstream=1. Receive heartbeats on 19015 and send replies on 19017.

5.5 RTSP Live Preview

After configuring and starting encoding, construct the RTSP URL using the camera IP address:

rtsp://<camera-IP>/ch1

Use a player or decoder that supports the selected codec, establish an RTSP session, and select TCP transport for audio and video. RTSP uses a separate connection; keep the control connection on 19017 and heartbeat connection on 19015 active. If the IP address or Wi-Fi network changes during preview, read the network information again, reestablish the TCP connections, and resume using the sequence TAG 0x6a → TAG 0x14 (pushstream=1) → RTSP.

6.2 SRT Configuration and Readback

Use 3.53.1 (TAG 0x69 / EXT TAG 0x01) to configure SRT, including enable, mode, port, latency, destination address, Stream ID, password, and AES encryption type. Listener and Caller share the same command and are selected by mode:

ModeField valueConnection behavior
Listenermode=0The camera listens on the configured port and waits for the receiver to connect.
Callermode=1The camera initiates a connection to the configured destination address and port.
  1. Read the configuration: send TAG 0x69 / EXT TAG 0x02 with only product_sn[24]; the device returns the complete SRT configuration.
  2. Start transmission: fill in the complete configuration, set enable=1, and send EXT TAG 0x01. delay is in ms, range 20 to 8000; fill in the other fields as defined in Chapter 3.
  3. Check the result: parse the setting response with the same EXT TAG 0x01. set_state=0 indicates success; 1 indicates failure. Send EXT TAG 0x02 to read back the configuration if required.
  4. Stop transmission: retain the required configuration, set enable=0, and send EXT TAG 0x01 again.

The setting response reports the parameter-setting result; the read command returns the configuration. Confirm an established SRT transmission connection using the receiver's connection and stream reception status. TAG 0x5c queries RTMP status.

6.3 RTMP Streaming and Connection Status

Use 3.31 (TAG 0x36) and app_set_rtmp_ext_t to configure the streaming URL, authentication, streaming switch, and startup option. Each fragment has a VALUE length of 246 bytes. enable=1 enables streaming; 0 disables it. PowerOnPushEn=1 enables streaming at startup; 0 disables streaming at startup.

  1. Configure and start streaming: fill in the target SN, a valid streaming URL, and authentication information. Set enable=1, configure PowerOnPushEn as required, and send TAG 0x36.
  2. Send URL fragments: each fragment carries up to 128 URL bytes. Start with url_offset=0 and increase the offset for subsequent fragments. Keep url_size and the control fields consistent throughout the configuration. Wait for the current fragment's setting response before sending the next fragment. The complete URL supports up to 511 content bytes. See 3.31.
  3. Read the configuration: send TAG 0x37 and use url_size, url_offset to reassemble the extended configuration URL and check the address, streaming switch, and startup option.
  4. Confirm the connection: send TAG 0x5c and read ConnectState; 2 indicates a successful connection. Interpret other values according to Section 3.43. The device does not push this status automatically; querying once per second is recommended.
  5. Stop streaming: send TAG 0x36 using the same extended payload format, set enable=0, and set the startup streaming option as required.

A successful TAG 0x36 setting response and a successful RTMP server connection are separate steps. Use TAG 0x5c to check the server connection and TAG 0x37 to read the saved streaming configuration.
